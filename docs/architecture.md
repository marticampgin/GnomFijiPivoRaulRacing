# Архитектура Gnom Fiji P.I.V.O Raul Racing

Статус: проектное предложение для реализации. Продуктовые решения ниже согласованы пользователем; выбор библиотек, протокола и численные параметры требуют технической проверки. Наличие этого документа не означает готовность сервера, платежей или игры.

## 1. Согласованные границы

- Godot, браузер на настольном компьютере первым; мобильное управление, адаптивный HUD и облегчённый профиль качества предусмотрены архитектурой.
- Полноценное одиночное прохождение: чемпионаты и сюжетная карта. Новые сюжетные тексты, персонажи и названия остаются заглушками.
- Публичные рейтинговые гонки и отдельные комнаты друзей. Комнаты не меняют публичный рейтинг.
- Подбор учитывает результаты предыдущих гонок и реальную силу установленного оснащения. Баланс важнее скорости заполнения лобби.
- Рейтинг может расти и падать; изменение зависит от места и силы соперников. +100 за победу и +70 за топ-3 являются исходными ориентирами, а не утверждённой фиксированной таблицей.
- Боты заполняют свободные места, соответствуют уровню лобби и дают столько же рейтинговых очков, сколько сопоставимые люди. Игрок не выбирает их сложность в рейтинге.
- Базовые характеристики нормализуются в онлайне, но установленные улучшения продолжают работать. Предмет может быть строго сильнее другого; обязательного обмена одного параметра на другой нет.
- Скорость, ускорение, управляемость, дрифт и прочность входят в модель машины. Все четыре стиля поддерживают ручной CTR-цикл: удержание одного плеча, до трёх турбо по таймингу противоположным, отпускание без ускорения.
- Очередь максимум из двух предметов, одна кнопка применения старшего. После успеха резерв сдвигается вперёд; при отказе порядок сохраняется. Дополнительного общего cooldown нет. Разные эффекты совместимы, одинаковый временный эффект обновляет длительность без сложения силы, мгновенные атаки и ремонт срабатывают каждый раз.
- Разрушение вызывает короткое возвращение на трассу и потерю времени, без окончательного выбывания.
- Бесплатная игра с магазином косметики, машин, персонажей, деталей, ускорителей прогресса и платных случайных кристаллов. Кристаллы могут выдавать машины и детали с характеристиками.
- Гость может начать знакомство; аккаунт нужен для рейтинга, покупок и переноса прогресса. При регистрации гостевой прогресс переносится.
- Первый внешний способ входа: Google. Локальная разработка и автоматические тесты должны работать без Google OAuth через изолированные тестовые профили; публичное окружение не допускает такой обход.
- Русские интерфейс и документация, английские идентификаторы в коде, локализация через ключи. Названия, бренды и лица исходной презентации сохраняются.

## 3. Границы исполнения

```text
Браузер: HTML shell + Godot Web
  | HTTPS: профиль, каталог, покупки, очередь, комнаты
  v
Meta API ---------------------------- PostgreSQL
  |                                    |
  | ticket + allocation                | outbox
  v                                    v
Race allocator                    Background worker
  |
  v
Godot headless race worker <------> Браузер Godot
  |    WebRTC / проверенный WSS
  |
  +-- authenticated result -------> Meta API

Платёжный провайдер -- verified webhook --> Meta API
Google -- ID token --> HTML shell -- HTTPS + CSRF --> Meta API auth
CDN -- versioned Web build + content --> Браузер
```

Клиент отправляет действия, а не готовые координаты, попадания, деньги или итоговое место. Backend выдаёт короткоживущий билет конкретного участника конкретной гонки. Worker принимает только билеты своего матча и выбранной версии сборки. Клиент не может вызвать внутренний endpoint результатов worker.

Первый деплой допускает один API-процесс и одну машину с несколькими race workers. API хранит назначения и аренду worker в БД; рестарт восстанавливает очередь из её состояния. Масштабирование до нескольких API требует координации через БД/блокировки; переход на отдельный брокер возможен по измеренной нагрузке.

### 3.1. Google-вход и собственная сессия

Для входа выбирается Google Identity Services (GIS) с ID token. Доступ к Gmail, Drive и другим Google API игре не нужен: Google access/refresh tokens не запрашиваются. Это аутентификация пользователя, а не разрешение игре читать его Google-данные. Разделение описано в [GIS Overview](https://developers.google.com/identity/gsi/web/guides/overview).

1. HTML shell показывает официальную кнопку Google. Backend создаёт короткоживущую попытку входа с криптографическим nonce, привязанную к текущей браузерной/гостевой сессии; shell передаёт nonce в GIS.
2. JavaScript callback получает credential и отправляет его через same-origin `POST /api/auth/google`. Backend проверяет Origin и прикладной CSRF token. В нашем callback/fetch нет автоматической защиты `g_csrf_token` встроенного GIS HTML POST, поэтому эти контракты не смешиваются.
3. `google-auth-library` проверяет подпись, разрешённый Google issuer, точный разрешённый audience и срок токена. Отдельно проверяется nonce и связь с попыткой входа; попытка потребляется однократно вместе с созданием сессии. Простого декодирования JWT недостаточно.
4. Аккаунт находится по `(provider, canonical_issuer, sub)`. Оба допустимых написания Google issuer нормализуются после проверки. Email является атрибутом профиля, не ключом личности и не основанием автоматического объединения аккаунтов.
5. Backend выдаёт собственную отзываемую сессию: случайный непрозрачный идентификатор в `HttpOnly; Secure; SameSite=Lax` cookie, с ротацией при входе, ограничением срока и серверным отзывом. В БД хранится hash идентификатора. Google credential не становится постоянным токеном API или билетом гонки.

HTML shell и `/api` публикуются под одним origin. Web-адаптер выполняет запросы с cookie, а Godot получает профиль/статус через узкий bridge, без чтения секрета сессии. Credential не попадает в save, URL, localStorage и логи. Для выбранного GIS flow Google client secret не требуется; публичный OAuth client ID находится в shell. Logout отзывает игровую сессию и отключает автоматический повторный выбор аккаунта в GIS; выход из самого Google и удаление игрового аккаунта являются отдельными действиями.

Вход и перенос гостя являются отдельными подтверждаемыми действиями. При переносе показывается целевой аккаунт, проверяется владение серверной гостевой сессией и выполняется существующая идемпотентная транзакция слияния. Переданный клиентом `guest_id` сам по себе не подтверждает владение. Связывание уже существующего аккаунта с Google требует доступа к обеим личностям; одинаковый email не даёт такого доступа. Отмена входа сохраняет гостя.

Основания для проверки токена и `sub`: [Google server verification](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token); контракт callback/nonce: [GIS JavaScript API](https://developers.google.com/identity/gsi/web/reference/js-reference). Политика собственной сессии, CSRF и слияния выше является решением проекта.

Мобильный браузер использует тот же Web-адаптер. Будущий native-клиент получает отдельный адаптер и OAuth client соответствующего типа, официальный SDK либо поддерживаемый системный browser flow, с PKCE для выбранного authorization-code flow. Встроенный WebView для Google OAuth не используем; модель аккаунта и provider subject остаётся общей. См. [Google native apps](https://developers.google.com/identity/protocols/oauth2/native-app).

Перед публичным тестом требуются Google Cloud project, Web client ID, разрешённые production origins, branding/privacy policy и проверки CSP/FedCM/popup в целевых браузерах. GIS загружается с официального `gsi/client`. Переход Godot на threaded Web export требует повторной проверки COOP и окна входа. См. [Google setup](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid).

### 3.2. Разработка без Google OAuth

`IdentityProvider` заменяет только внешний способ подтверждения личности. `DevIdentityProvider` позволяет выбрать несколько заранее созданных тестовых профилей без Google-аккаунта, Google Cloud project и client ID. Он выдаёт обычную игровую сессию; авторизация API, проверка владения, guest merge, ротация/отзыв сессий и работа инвентаря выполняются теми же модулями backend. Это не глобальное отключение проверок.

| Граница | Правило |
| --- | --- |
| Включение | Только явно заданное deployment environment `local`/`test` вместе с `DEV_AUTH_ENABLED=true`. Одного `NODE_ENV=development` недостаточно; неизвестное окружение не включает dev-вход. |
| Тестовые личности | Отдельный `provider=dev`, отдельный issuer и разрешённые fixture IDs. Запрос не задаёт произвольные account ID, роль, баланс или Google subject. |
| Сеть | Local API и опубликованные порты контейнера по умолчанию привязаны к loopback. POST требует Origin/CSRF и ограниченного CORS даже на localhost. |
| Изоляция | Отдельная dev/test БД и session configuration; проверяемый environment marker БД. Dev-профили не связываются с Google и не мигрируют в production. |
| Публичная среда | В production и публичном staging нет dev-маршрута и кнопки. Dev-флаг/провайдер вызывает отказ запуска; API отклоняет dev identities/sessions даже при ошибочном переносе данных. |
| Cookie | `HttpOnly` и SameSite сохраняются. Ослабление только `Secure` для локального HTTP допускается исключительно в `local`/`test`, никогда на публичном хосте. |

Нельзя активировать dev-вход через query string, клиентский заголовок или `dev=true` в JSON. CI отдельно проверяет обычный production boot с ответом 404 на dev endpoint и отказ старта при запрещённом флаге. Успешный dev-вход не подтверждает интеграцию Google: реальный Google flow остаётся отдельным критерием публичного выпуска.

## 5. Вождение и изменяемые трассы

Движение опирается на физический движок Godot. На этапе исследования сравниваются встроенный `VehicleBody3D` и аркадный контроллер на `RigidBody3D`/`CharacterBody3D`; готовый контроллер допускается после проверки лицензии, Web export и совместимости с сервером. Свою библиотеку столкновений не разрабатываем.

Godot предупреждает об ограничениях `VehicleBody3D` для сложной физики машины. Поэтому его выбор не фиксируется до проверки дрифта, прыжков и перевёрнутых участков. Источник: [VehicleBody3D](https://docs.godotengine.org/en/stable/classes/class_vehiclebody3d.html).

`VehicleStats` содержит `top_speed`, `acceleration`, `handling`, `drift`, `durability`;
текущий численный baseline приведён в [playtest-balance](playtest-balance.md).
Удерживаемые `drift_left`/`drift_right` проходят в общую физику локального режима,
prediction, worker и ботов. `RacingVehicle` хранит инициирующее плечо, предыдущие
held-состояния обоих плеч, заряд, число успешных турбо, блокировку после промаха
и сигналы HUD. Всё это входит в `capture_state`/`restore_state`: повтор последнего
пакета и replay не создают нового нажатия. До трёх противоположных свежих нажатий
в окне дают boost; отпускание никогда его не выдаёт. Поворот нужен для входа,
но активный дрифт допускает выпрямление/контрруление; заряд требует контакта,
достаточной скорости и реального скольжения. Полёт, восстановление, блокировка
движения и пауза отменяют цикл без награды. Точная настройка остаётся предметом плейтеста.

Модель трассы задаёт локальную опорную поверхность и направление притяжения. Это позволяет проектировать стены, петли и 360-градусные элементы без предположения, что мировой `Y` всегда направлен вверх. Камера плавно следует опорной системе и имеет профиль уменьшенной тряски.

Изменение трассы оформляется как `TrackEvent(event_id, activation_tick, state, collision_revision)`. Сервер меняет проезд и коллизии на известном тике; клиент синхронизирует геометрию, предупреждения и эффекты. Отдельно проверяются машины на границе участка, появление препятствия внутри машины, respawn и обновление AI-маршрута. Не передаём физически произвольную новую геометрию каждый кадр.

## 6. Сеть и целостность гонки

Godot WebRTC встроен в Web, но на native-платформах требует `webrtc-native` GDExtension; обмен SDP/ICE выполняет signaling. WSS использует TCP и может задерживать новые сообщения за потерянным старым. Документация [WebRTC](https://docs.godotengine.org/en/stable/tutorials/networking/webrtc.html) отмечает это различие; страница помечена как не полностью обновлённая, поэтому совместимость конкретной версии расширения проверяется сборкой Linux worker.

Топология всегда клиент-сервер: WebRTC не означает, что один игрок становится доверенным хозяином. Боты работают внутри worker. Надёжный канал переносит start/finish, предметы и события; частые inputs/snapshots допускают пропуск устаревших пакетов. Для WSS нужны ограничение очереди и отбрасывание устаревшего состояния до отправки; это не устраняет блокировки TCP.

| Контракт | Минимальные поля | Проверка получателем |
| --- | --- | --- |
| `JoinTicket` | `match_id`, `player_id`, `loadout_hash`, `protocol_version`, `expires_at`, подпись | Матч, срок, подпись, однократный вход/валидное переподключение |
| `InputFrame` | `type=input`, `sequence`, `steering`, `throttle`, `brake`, `drift_left`, `drift_right` | Диапазоны, порядок, частота, принадлежность игроку; отдельные held-флаги плеч |
| `ItemCommand` | `type=use_item`, `sequence`, `race_id`, `epoch` | Идемпотентность, голова FIFO на сервере, состояние гонки; номера слота нет |
| `WorldSnapshot` | `server_tick`, подтверждённые inputs, машины, состояние трассы | Версия протокола, актуальность тика |
| `RaceEvent` | `event_id`, `tick`, тип, данные | Дедупликация и порядок для надёжных событий |
| `MatchResult` | `match_id`, версия баланса, состав, оснащение, места, DNF, hash событий | Только удостоверенный worker с активной арендой; результат уникален |

Prediction применяется к своей машине, interpolation к соперникам. Серверные snapshots исправляют ошибки. Не предполагается битовая детерминированность физики разных браузеров; запись серверных событий и периодических snapshots обеспечивает разбор спорных результатов.

Текущий совместимый baseline: wire 9, vehicle state 2, loadout `prototype-v13`,
vehicle balance `vehicle-prototype-v13`. Изменение формата двух плеч и FIFO
несовместимо с wire 8 и отклоняется на входе. Клиент ограничивает отправленные
неподтверждённые inputs до 24 при серверной очереди 30, сохраняя переходы плеч
до появления кредита; это не разрешение серверу выполнить несколько физических
шагов за один tick. Старый slot-параметр не является поддерживаемым обходом FIFO.

Скрытая вкладка может перестать исполнять симуляцию. Worker продолжает гонку: после таймаута ввода применяет нейтральное управление/утверждённую замену ботом, возвращение клиента восстанавливает состояние. Окно переподключения, штраф DNF и поведение замены пока параметры настройки, но выход не отменяет уже зафиксированное участие и не позволяет избежать рейтингового результата.

Стартовые гипотезы для испытаний: физика 60 Hz, snapshots 15-20 Hz, полное лобби до 10 машин. Это цели эксперимента, не подтверждённые показатели. Проверка при потерях, задержках и TURN решает выбор транспорта до производства большого объёма контента.

## 7. Прогресс, сборки и подбор

`campaign_stats = vehicle_base + progression + equipment + allowed_synergies`.

`online_stats = normalized_vehicle_base + online_equipment_effects + allowed_synergies`.

Нормализация убирает прямой перенос уровня кампании в базу, но не превращает все машины в одну. Отличия архетипов и экипировки сохраняются. Сильная деталь не обязана иметь отрицательный эффект: она повышает измеряемую силу сборки. Конкретные коэффициенты нормализации являются версионированными данными баланса.

Сервер вычисляет `assembly_strength` из итоговых параметров, синергий и тестов поведения на разных трассах. Простая сумма редкостей непригодна: редкость не равна влиянию на время круга. Для подбора сохраняются и итоговая оценка, и вектор характеристик. Модель силы уточняется по результатам тестовых ботов и живых гонок; версия записывается вместе с матчем.

Порядок подбора: совместимые регион/задержка/версия -> близкое оснащение -> близкий рейтинг результатов -> ограниченное расширение диапазона -> заполнение ботами сопоставимого уровня. Сборка блокируется при вступлении в очередь; изменение деталей отменяет старую заявку и пересчитывает её. Более быстрый старт не должен сводить заведомо несопоставимые машины.

`rating` остаётся показателем результатов и может снижаться. Начальный кандидат сравнивает фактическое место с ожидаемым результатом против каждого участника; оснащение ограничивает подбор отдельно:

```text
expected_ij = 1 / (1 + 10 ** ((rating_j - rating_i) / D))
actual_ij = 1 if i finishes ahead of j, 0 if behind, 0.5 if tied
delta_i = round(K * average(actual_ij - expected_ij))
```

Это схема для калибровки, не окончательная математическая модель. Кандидат D=400, K=200 и его примеры описаны в game-design.md. Лимиты, ничьи, DNF и таблица примеров утверждаются после симуляции. Если остающееся различие оснащения требует поправки ожидаемого исхода, её добавляют как отдельную проверяемую модель; нельзя дважды компенсировать одно преимущество.

Боты входят в расчёт как сопоставимые соперники без понижающего коэффициента награды и получают сервером зафиксированную оценку уровня. Правило допуска лобби с единственным человеком (`ranked_min_humans`) остаётся открытым до публичного теста; равные очки за ботов сами по себе не определяют этот порог. Высокий рейтинг не должен выращиваться бесконечными победами над слишком простыми ботами: проверяются калибровка их сложности, рост требований и расхождение результатов против людей/ботов. Изменение самих правил награды требует согласования.

Покупка создаётся на backend по цене сервера. Подтверждение в браузере после checkout не выдаёт товар; выдача следует из проверенного webhook провайдера. Повтор webhook, повтор POST и обновление вкладки возвращают тот же результат. Откат/возврат оформляется отдельной компенсирующей записью, без удаления истории.

Открытие кристалла выполняется сервером: блокировка кошелька/расходуемого объекта -> проверка ключа операции -> списание -> выбор из закреплённой таблицы серверным криптографическим RNG -> выдача -> сохранение результата в одной транзакции. Анимация лишь показывает уже определённый результат. Повтор запроса никогда не даёт новый бросок. Экран до оплаты показывает возможные награды и вероятности; правила дубликатов задаются каталогом и явно отображаются.

Объединение гостя с аккаунтом имеет уникальный `merge_id` и транзакцию: блокируются оба профиля, засчитываются только доверенные серверные награды гостя, выдачи объединяются по источникам, прогресс по правилам узлов. Затем гость помечается перенесённым. Повтор не увеличивает валюту. Локальный save не является доказательством покупки или награды.

Одиночная тренировка может исполняться локально. Прохождение, выдающее общую с платным магазином валюту/инвентарь, требует онлайн-подтверждения сервером. Предлагается повторно использовать race worker для наградных гонок кампании; стоимость измеряется до массового запуска. Полноценное офлайн-прохождение с переносом наград пока не обещается.

Итог гонки сохраняется одной транзакцией: уникальный результат -> награды -> изменение рейтинга только для публичного рейтингового режима -> outbox. Повтор worker после таймаута не создаёт вторую награду. Политика при аварии worker: матч помечается прерванным, частичные результаты не рассчитываются как обычный финиш; повторная обработка видна в мониторинге.

### 8.1. Почему PostgreSQL

PostgreSQL остаётся основным хранилищем: аккаунты, личности Google, сессии, владение, кошелёк, покупки, прогресс и рейтинговые результаты связаны общими инвариантами. [Транзакции](https://www.postgresql.org/docs/current/tutorial-transactions.html) позволяют атомарно фиксировать списание и выдачу; [ограничения](https://www.postgresql.org/docs/current/ddl-constraints.html) защищают уникальность операции и связи. Конкурентные списания дополнительно требуют блокировок или условных обновлений и тестов повторов: наличие SQL-транзакции само по себе не решает гонку запросов.

Физика, текущие позиции, inputs и snapshots живут в памяти Godot worker, не записываются в PostgreSQL каждый тик и не ждут SQL на критическом пути симуляции. В БД попадают долговечные события и подтверждённые результаты. Тяжёлые replay/телеметрические файлы не смешиваются с транзакционными таблицами: их отдельное хранилище вводится при появлении измеренной потребности.

На старте нужны миграции, индексы, ограниченный пул соединений, ограниченные batch outbox, мониторинг запросов и проверяемое восстановление из резервной копии. Redis/брокер не добавляем без конкретного узкого места. PostgreSQL поддерживает Linux/ARM; выбор этой БД не требует x86-сервера. Источники: [Supported platforms](https://www.postgresql.org/docs/current/supported-platforms.html), [Backup and restore](https://www.postgresql.org/docs/current/backup.html). При совместном размещении с гонками БД получает отдельный бюджет RAM/CPU и диска.

### 8.2. Реализованный фундамент постоянных данных

Этап 4.2 добавляет миграцию `002_progression.sql` и внутренний `ProgressionService`,
не подключая награды к локальной гонке. История миграций хранит SHA-256 SQL;
последовательное применение, проверка окружения и dev seed выполняются одной
транзакцией под advisory lock. База с прежней `001_auth.sql` обновляется без
удаления аккаунтов и сессий; изменённая применённая миграция отклоняется.

Каталог публикуется целой неизменяемой версией. ID права владения стабилен между
версиями; определения закреплены за версией. Инвентарь на этом этапе содержит
только постоянные нерасходуемые права на машины, персонажей, детали и косметику.
Один серверный `operationId` выдачи соответствует одному неизменяемому payload;
повтор возвращает прежний результат. Журнал и владение фиксируются атомарно,
конкурентные выдачи одному аккаунту сериализуются. Повторное владение отражается
в журнале, не порождая вторую запись инвентаря; это не правило компенсации
платных дублей. Кошелёк, расходуемые предметы и платёжные операции ещё отсутствуют.

Сборка закрепляет версию каталога и один из четырёх стилей. Составные внешние
ключи проверяют владение тем же аккаунтом и наличие детали в выбранной версии.
Конкретные слоты, совместимость, параметры деталей и синергии не утверждаются
этой схемой. Гараж и серверная оценка мощности остаются задачами 4.4/4.5;
`prototype-v13` в билете по-прежнему обозначает общую совместимость симуляции.

Публикация/выдача доступны только как внутренние функции backend, без HTTP route
и без наполнения реального каталога. Гость не получает права из локального save;
существующий перенос пока охватывает только серверный счётчик тренировок.
Временные осколки гонки не попадают в эти таблицы. Это фундамент, а не готовая
кампания, экономика, Google-вход или магазин.

## 9. Интерфейс и мобильная подготовка

Экранные потоки: гостевой старт -> хаб -> чемпионаты/карта, гараж, публичная очередь, комнаты, магазин, профиль -> гонка -> результаты. Вход/регистрация запрашиваются перед рейтингом и покупкой. Текущая поставка макетов покрывает восемь основных экранов и ключевые состояния отдельным листом. Полный набор состояний компонентов перед реализацией включает ожидание, ошибку сети, пустой инвентарь, недостаток валюты, повторное подключение и подтверждение успешной выдачи; наличие главного экрана само по себе не означает завершённость этого набора.

`InputFrame` одинаков для клавиатуры, геймпада и будущего touch adapter;
управление не обращается к DOM напрямую. HUD показывает активный предмет крупнее
следующего, одну команду применения, окно тайминга и три отметки турбо.
Будущий touch adapter должен сохранить FIFO и два различимых действия дрифта,
без независимого выбора резерва; конкретная компоновка проверяется на мобильном этапе.

Оболочка предпочитает первый доступный геймпад для нового P1 до гонки, сохраняя
явный выбор и владение устройствами другими местами. Browser Gamepad API может
открыть устройство только после первого взаимодействия в активной странице.
Hot-plug не должен сбрасывать фокус и настройки. Навигация выбирает геометрического
соседа, подсказки соответствуют текущему устройству; A/B означают подтверждение/назад,
а результаты маршрутизируют A непосредственно собственному месту. Подключение
во время гонки не крадёт устройство и не продолжает игру после отключения само.

Строки хранятся через стабильные localization keys. Русские макеты проверяют длинные названия, цифры рейтинга и цены. Новые сюжетные узлы помечаются «Глава 01», «Соперник: TBD»; рабочие заглушки не выдаются за согласованный сюжет. Цвета не являются единственным способом отличать предметы/опасности.

## 10. Проверки и эксплуатация

- Unit: нормализация, совместимость деталей, эффект refresh/stack, FIFO и парный CTR-цикл, рейтинг для одинаковых входов людей/ботов.
- Integration: повтор результата, webhook и открытия кристалла; конкурентное списание; повтор guest merge; изменение loadout в очереди.
- Auth: Google signature/iss/aud/exp, чужой/повторный nonce, CSRF, отмена входа, отсутствие auto-link по email, ротация/logout; dev login без Google configuration, запрет произвольного fixture/роли, отсутствие dev endpoint и отказ dev session в production.
- Godot headless: старт и финиш гонки, чекпоинты, последовательное применение предметов и отказ без перестановки, destruction/respawn, трансформация трассы с ботами; симметрия плеч, три турбо, ранний/поздний промах, удержание, пауза и replay.
- Browser: реальный Web export в Chromium/Firefox/Safari, потеря фокуса, reconnect, геймпад, первая активация звука, изменение размера окна.
- Load/network: 10 участников, потери и задержки, TURN, ограничение памяти, длительный запуск, ошибка worker и повтор доставки результатов.
- Экономика: распределения выдачи на тестовой выборке, фиксированные odds/version, отсутствие двойного списания/выдачи, возвраты.

Наблюдаемость: время подбора, расхождение силы соперников, доля ботов, rating drift между матчами с людьми и ботами, задержка ввода, число corrections, frame time, сбои загрузки, стоимость минуты гонки, покупки/выдачи с задержкой, ошибки worker. Логи не содержат платёжных секретов или токенов сессий.

Регионы и число workers увеличиваются по загрузке и длине очередей. Worker получает лимит матчей/ресурсов; capacity недоступна -> явное состояние ожидания без ложного старта гонки. Каталог, правила экономики и протокол версионируются; незавершённые матчи завершаются на своей версии. Откат клиента не должен откатывать журнал покупок.

### 10.1. ARM64, 4-8 ядер и проверка вместимости

Linux ARM64 подходит как целевая платформа прототипа: [Godot 4.7 Linux export](https://docs.godotengine.org/en/4.7/classes/class_editorexportplatformlinuxbsd.html) включает arm64, а headless-сервер не требует GPU. Картинку рисует браузер игрока; сервер считает физику, ботов и правила. Для production выбирается dedicated release export со снятыми визуальными ресурсами, сохраняя нужные для физики данные.

`webrtc-native` 1.2.1 является кандидатом: [релиз](https://github.com/godotengine/webrtc-native/releases/tag/1.2.1-stable) заявляет Godot 4.3+, [release matrix](https://github.com/godotengine/webrtc-native/blob/1.2.1-stable/.github/workflows/build_release.yml) включает Linux ARM64. Это не заменяет проверку конкретных Godot 4.7.2, GDExtension и ОС. Работу нашей сборки на Linux ARM64 пока не проверяли.

Число ядер не определяет вместимость. Нужны модель CPU, выделенные или shared vCPU, RAM, SSD, CPU steal/throttling и сеть. API, PostgreSQL, TURN и race workers на одном хосте конкурируют за ресурсы. 8 ядер не гарантируют вдвое больше гонок, чем 4. Наградная кампания с одним человеком и ботами также занимает worker и входит в расчёт стоимости.

План проверки конфигураций на 4 и 8 ядрах:

1. Зафиксировать CPU/RAM/ОС и хэши release-сборок. Проверить нативный ARM64 startup, загрузку GDExtension, браузерное соединение напрямую и через принудительный TURN.
2. Запустить репрезентативную трассу с 10 машинами, дрифтом, столкновениями, предметами и событием трассы. Отдельно проверить бот-нагрузку и реальных сетевых клиентов с другой машины.
3. При гипотезах 60 Hz physics / 15-20 Hz snapshots собирать p50/p95/p99 длительности работы тика, пропуски бюджета 16.67 ms, отставание симуляции, RSS, CPU по ядрам, сеть и очереди сообщений. Измеряется весь критический путь, включая физику, AI и сетевую обработку, а не только время пользовательского `_physics_process()`.
4. Увеличивать число параллельных workers по одному, одновременно нагружая API/БД, проверять рестарт worker и повтор доставки результатов.
5. Начальные критерии для испытаний: p99 работы тика не выше 12 ms, пропуски дедлайна менее 0.1%, отсутствие растущего отставания/OOM/swap и минимум 20% ресурсного запаса. Прогон после прогрева не короче 30 минут, финальная проверка стабильности не короче 2 часов. Это предложенные бюджеты, не достигнутые показатели.
6. Лимит allocator устанавливается по последнему полностью успешному прогону. Отчёт отдельно указывает гонки, человеческих игроков, ботов и наградные кампании; пустой worker или тест только ботов не подтверждает ёмкость реального онлайна.

До этого теста не обещаем число одновременных игроков или фиксированную стоимость сервера. Выделенный Linux ARM64 хост/доступ ещё не предоставлен; локальный headless startup не является его нагрузочной проверкой.
